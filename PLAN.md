# ai-delivery-playbook — Plan

*Public playbook of skills/workflows/lifecycle docs for AI-assisted delivery. Current focus: keep the skill set grounded in real usage (this repo dogfoods its own conventions — self-assigned `AIPB-NN` IDs, `trivial/`/`chore/`/`feature/` branches, no speculative features) rather than growing it ahead of a concrete need.*

## Status

- **Spec-anchored task files** landed in [AIPB-22](./tasks/AIPB-22.md) — the first step of making spec-driven development (SDD) the default working style (decided 2026-10-29). Task files are kept, not deleted: closed out when the PR opens, linked by `Updated by` / `Superseded by` when a later ticket changes the same behavior, and moved to a visible `tasks/` folder. The rules live in `AGENTS.md` → Task file lifecycle; `/commit`, `/create-task` and `/implement-task` enforce them. Every AIPB ticket now has a task file, indexed in [`tasks/README.md`](./tasks/README.md): 11 restored from git history (`git log --full-history` is needed to see AIPB-03, 04 and 06, whose files were added and deleted on their own branches), 10 reconstructed from PRs and commits and marked as such. This repo publishes them; nothing new is exposed, since every restored file was already public in history.
- **Post-mortems** joined them in [AIPB-23](./tasks/AIPB-23.md): `/postmortem` keeps a blameless Markdown post-mortem at `tasks/postmortems/TICKET-ID.md`, linked both ways with the ticket's task file (`**Task:**` / `**Postmortem:**`). The post-mortem is committed; only the raw scratch notes stay out of git, and the wiki is an optional copy. Worked examples stay (how a run went) and link their task files (what was decided and why) both ways. `done` means the PR exists; `/branch-cleanup` Step 8 reads the merge state live and reports mismatches.
- **`/perf-check`** ([AIPB-32](./tasks/AIPB-32.md)) measures web pages the same way every time (pinned Lighthouse, mobile and desktop, median of several runs) and reads the causes. It ran live on two sites before it was written; its CI gate, real-visitor data and native mobile apps are marked not yet proven in [`docs/web-performance.md`](./docs/web-performance.md).
- **MCP governance for unattended runs** ([AIPB-33](./tasks/AIPB-33.md)): in a cloud or headless run an allowlist entry is the approval, so [`docs/mcp-governance.md`](./docs/mcp-governance.md) says to name tools, gate writes with a deny rule or a pre-tool-use hook, and check what a client remembers. A hook beating an allow, a deny flag beating a saved approval and saved per-folder approvals were run live in one client; the cloud agent behaviour is from documentation only and marked not yet proven.
- 24 skills documented in [`skills/`](./skills/), all tool-agnostic in [`AGENTS.md`](./AGENTS.md) with `CLAUDE.md` as a thin import shim.
- [`/github-actions-setup`](./skills/github-actions-setup.md) added (AIPB-24) from a real solo-project setup. It covers checks on every PR, a PR hygiene check (ticket ID with matching branch and task file, a description, tests alongside changed source), a deploy on merge of the checked build, and a label-triggered read-only AI review. It narrows `lifecycle/release.md`'s Gap to rollout/rollback: the deploy after a merge now has a skill, while how a change reaches users still doesn't.
- `/github-actions-setup`'s first real adoption is traced in [`examples/AIPB-24.md`](./examples/AIPB-24.md) (AIPB-25). All four jobs ran; every failure was in the one-time secret setup, none in the workflows. Its lessons are in the skill (the AI review's credential and failure signature), in a new `AGENTS.md` section on secrets a person stores, and in `review-pr` / `review-comment-style` (inline comments only on diff lines, an author can only Comment on their own PR, never link generated folders into a review worktree).
- **This repo's own CI** (AIPB-26, [`docs/ci.md`](./docs/ci.md)):
  - every PR runs the MCP tests and a docs check (skill frontmatter, registration in all places, relative links) plus PR hygiene;
  - a PR from this repo gets a testing deploy of the MCP server at its own `pr-<n>` address;
  - a merge deploys the real server from GitHub Actions instead of Cloudflare's Git build;
  - the Claude review runs on a label.

  `/github-actions-setup` gained the testing-deploy step from it.

Coverage gap stated plainly in the scorecard itself: the "delete" path is thoroughly verified, "no PR found" and "host unavailable" have zero real cases yet — extend when they occur for real, don't invent them.

## Next up

- **SDD — what's left.** How the existing skills map onto spec-driven development's stages. Command names are GitHub Spec Kit's, re-checked 2026-11-09 against v1.3.3 (sources below):

  | SDD stage (Spec Kit) | Already here |
  |---|---|
  | Constitution (`/speckit.constitution`) | [`CONSTITUTION.md`](./CONSTITUTION.md) (AIPB-29), checked by `/create-task` and `/review-pr` |
  | Specify (`/speckit.specify`) | `/analyze-story`, `lifecycle/requirements.md`; `/define-slo`, `/security-check` for non-functional requirements |
  | Clarify (`/speckit.clarify`) | "Research Before Implementing" + Open questions |
  | Plan (`/speckit.plan`) | `/create-task`, `/design-brief`, `/diagram` |
  | Tasks (`/speckit.tasks`) | `/analyze-story` subtasks, the task file's plan |
  | Implement (`/speckit.implement`) | `/implement-task` |
  | Analyze (`/speckit.analyze`) / verify | `/verify-browser`, `/test-scaffold`, `/security-check`, `/review-pr`, `/agent-eval` |
  | Living docs (no Spec Kit command) | `/code-doc`, `/plan-update` |

  Remaining:
  - **Spec trail in practice:** the `Updated by` links only pay off once new tickets search `tasks/` for earlier specs (`/create-task` Step 5). Check after the next few tickets whether that search actually finds and links anything; tighten the step if not. First real run, AIPB-23: it found AIPB-22 (which had parked the `.postmortems` question) and linked it; `/postmortem` itself had no earlier spec, since it came in a `TRIVIAL` commit.
  - **Two Spec Kit stages not mapped yet:** `/speckit.checklist` and `/speckit.converge`. Read what each does in Spec Kit's docs before deciding whether something here covers it.

- **Release ≠ deploy** — `lifecycle/release.md` currently defines Release as "PR merged, ticket closed" with no rollout/rollback/flag-lifecycle content; feature flags exist only as an `implement-task` implementation mechanic (register + on/off check), not a release strategy. Candidate next ticket after AIPB-20: a `create-task` addition (or a `release-plan`-style skill, TBD) covering rollout/rollback decided before merge, flag lifecycle (a flag created without a removal ticket is debt), and why flags alone don't protect data (schema/API changes need expand-contract, not just a toggle) — this playbook's own mobile focus makes this sharper than it would be for web-only: a shipped app binary can't be rolled back, and old app versions keep calling the API for months.
- **Vendor-neutral "context weight" descriptor per skill** — not "use Sonnet here," which would hard-code one vendor's model names into 19+ tool-agnostic skill files, but something like "judgment-heavy, needs broad context" vs. "mechanical, narrow context once a spec exists" as a skill-frontmatter or table descriptor, so whoever's running a skill (with whatever tool/model) can decide their own delegation. Not started — needs its own real trigger before building (same AIPB-02 bar), likely a real cheap-model-delegation experiment first, same as `/agent-eval`'s "run it for real before writing the doc" precedent from AIPB-19.

## Decision points

- **`/github-actions-setup`'s next adoption:** the first ran on Cloudflare Pages (`examples/AIPB-24.md`). The second, this repo's own (AIPB-26), ran on Workers, adding a testing deploy per PR. Its preview alias, deploy and token check held on their first runs. When it reaches a host outside Cloudflare (Vercel, Netlify), check the deploy table's commands there and fix the skill where they don't hold.

- **Reference-architecture level (docs/future-considerations.md):** revisit once a second real adoption in a different stack exists — not before.
- **`/agent-eval` golden sets:** build one only once a skill has real usage history behind it, per the skill's own guardrail — not on day one for any new skill. First one built for `branch-cleanup` (AIPB-20 cycle); extend its "leave alone"/"no PR found"/"host unavailable" coverage the first time a real case of each occurs, don't invent examples to fill the gap early.
