# Worked Example: AIPB-19 — Worktree-isolated parallel agents, live

**Trigger:** Earlier research (surfaced in a separate session, generalized into `docs/future-considerations.md`'s "personal AI-tooling decision log" entry) flagged git-worktree-based parallel agents and orchestrator/sub-agent patterns as one of 2026's most concrete trend shifts in agentic coding. Rather than write the pattern up speculatively, the actual test was to run it for real against this repo first — same AIPB-02 bar as everything else here: a real trace beats a documented hypothesis.

**Workflow:** none of the existing three (`feature-delivery`/`bugfix`/`design-system-update`) — this is new Agent Orchestration mechanics, not a delivery workflow.

## Trace

1. **Checked for an existing gap before building anything.** `AGENTS.md`'s Agent Orchestration section already covered two things: never let two agents write the same files concurrently (serialize instead), and the positive counterpart — fanning out *read-only* checks (lint/tests) in parallel. Neither covered running genuinely independent *write* work concurrently via isolated worktrees. Confirmed via grep that no doc anywhere in the repo mentioned "worktree" before this ticket.
2. **Found two real, independent, file-disjoint tasks — ruling out a false lead first.** Considered documenting a suspected gap (examples/ skips AIPB-05) before checking git history — `git log --all | grep AIPB-05` showed the ID was simply never used (sequence jumps 04→06 in real history), not a missing worked example. Correctly discarded rather than assigned as agent work. Landed on two real, verified candidates instead: a `CONTRIBUTING.md` addition (documenting the skill+doc pairing pattern that's emerged organically across three real tickets — AIPB-15/17/18) and a full relative-markdown-link integrity audit (warranted given how much cross-linking the last several tickets added rapidly).
3. **Spawned both as background agents with `isolation: "worktree"`, in one message.** Each briefed explicitly on what file(s) were out of scope and *why* — "a parallel task is using them" — per the rule this ticket itself was about to add to `AGENTS.md`. Neither agent was told about the other's specific findings, only that a parallel task existed.
4. **Both returned real, honest results — not manufactured ones.** The `CONTRIBUTING.md` agent made one clean, well-scoped commit on its own branch. The link-audit agent checked 172 relative links, found zero real breaks, correctly identified the repo's one *documented* exception (`.tasks/*.md` links to deleted-on-merge task files) plus one *undocumented* one it reasoned through independently (`AGENTS.md`'s Package Map template placeholders, which don't resolve on purpose) — and made **no commit at all**, since an empty branch just to look productive would be worse than an honest null result.
5. **A real bug surfaced from running the pattern itself, not from either agent's assigned task.** Exiting the first agent's worktree left `.claude/worktrees/` sitting untracked in the parent repo — `.gitignore` had never accounted for worktree state or `.claude/settings.local.json` (which `CLAUDE.md` already says must never be shared). Fixed and shipped separately (its own ticket-less `trivial/` branch), since it's infrastructure hygiene, not part of either agent's actual assignment.
6. **Merged both real branches back individually**, each as its own PR — worktree isolation prevented a file collision, it didn't substitute for reviewing each diff before it landed.
7. **Wrote the pattern into `AGENTS.md`'s Agent Orchestration section** (new "Worktree-Isolated Parallel Agents" subsection) and a matching `docs/vocabulary.md` entry, *after* running it for real — this document is that write-up.

## What this run actually validated

The honest-null-result agent is the more important half of this trace, not the one that produced a commit. A parallel-agent pattern that only gets demonstrated by its successes teaches "spawn agents and they'll produce useful diffs" — the real lesson is closer to "spawn agents, brief them not to invent work, and trust the ones that come back empty." The `.gitignore` gap is the other real signal: running the mechanism for the first time immediately surfaced an infrastructure gap neither agent's task was looking for — exactly the kind of thing a purely theoretical write-up would have missed.
